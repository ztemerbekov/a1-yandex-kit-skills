# Техническое устройство

Корневой README описывает пользовательские задачи. Здесь собраны внутреннее устройство, покрытие API и эксплуатационные ограничения проекта.

## Компоненты

Проект состоит из трёх уровней:

1. **`yandex-kit-core`** — типизированный клиент публичного API Яндекс KIT. Реестр операций и типы генерируются из сохранённой OpenAPI-спецификации.
2. **`mcp-yandex-kit`** — stdio MCP-сервер, который предоставляет операции клиента AI-приложению.
3. **Agent Skills** — инструкции для выбора операций и выполнения пользовательских сценариев. Шесть навыков отвечают за домены API, четыре — за готовые сценарии магазина, один — за установку.

## Покрытие API

| Показатель | Значение |
| --- | ---: |
| MCP-инструменты | 71 |
| Операции со специализированными инструментами | 75 |
| Операции без специализированного инструмента | 86 |
| Всего операций в сохранённой спецификации | 161 |
| Agent Skills | 11 |

Число инструментов и число специализированных операций не обязаны совпадать: один инструмент может выбирать несколько связанных операций по действию.

Для операций без отдельного инструмента используется мета-трио:

- `search_operations` ищет операции по `operationId`, пути, тегу и русскому описанию;
- `get_operation_schema` возвращает метод, путь, параметры, content type и развёрнутые схемы запроса и ответа;
- `kit_request` выполняет операцию по `operationId`.

Полная карта инструментов и список остальных 86 операций генерируются в [TOOLS.md](TOOLS.md).

## Проверка запросов

- JSON-тела специализированных write-инструментов и `kit_request` валидируются по JSON Schema сохранённой OpenAPI-спецификации с помощью AJV до обращения к сети.
- Пустые обновления отклоняются.
- Для каждой операции используется указанный в спецификации content type, включая `application/merge-patch+json` и `multipart/form-data`.
- Read-only инструменты помечаются аннотациями для MCP-клиента.
- `kit_request` предоставляет полный доступ к API и поэтому сам по себе не считается read-only: безопасность определяется выбранной операцией.

Навыки добавляют поверх этого поведенческую границу: обзорные запросы не вызывают write-инструменты, а бизнес-значения для изменений не выводятся из догадок.

## Сетевой клиент

Клиент использует Bearer-токен и по умолчанию:

- ограничивает поток до 3 запросов в секунду;
- применяет таймаут 30 секунд к каждой попытке;
- автоматически проходит пагинацию там, где это предусмотрено обёрткой;
- повторяет только GET-чтения после сетевой ошибки, таймаута, HTTP 429, HTTP 5xx или ошибки `LIMIT_EXCEEDED`;
- учитывает `Retry-After`, когда сервер его возвращает;
- использует экспоненциальную задержку между остальными повторными попытками.

Каждый MCP-процесс имеет собственный limiter; параллельные сессии одного магазина
могут суммарно превысить лимит API. Общего межпроцессного limiter нет.

`LIMIT_EXCEEDED` у Яндекс KIT может приходить как HTTP 400. POST, PATCH, PUT и DELETE не повторяются автоматически: после таймаута сервер мог уже применить изменение, а повтор создал бы дубликат или вторую мутацию.

## Конфигурация сервера

| Переменная | Обязательна | По умолчанию | Описание |
| --- | :---: | --- | --- |
| `YANDEX_KIT_TOKEN` | env-режим | — | API-токен; в проектном режиме игнорируется. |
| `YANDEX_KIT_BASE_URL` | нет | `https://api.kit.yandex.net` | Базовый URL только для env-режима. |
| `YANDEX_KIT_CONNECTIONS_DIR` | нет | `~/.a1-yandex-kit/connections/` | Приватное хранилище проектных подключений. |
| `YANDEX_KIT_RPS` | нет | `3` | Пропускная способность token bucket, запросов/с. |
| `YANDEX_KIT_TIMEOUT_MS` | нет | `30000` | Таймаут одной HTTP-попытки, мс. |
| `YANDEX_KIT_TELEMETRY` | нет | включена | `0`/`false`/`off` отключает телеметрию использования. |

Прежний env-запуск опубликованного сервера:

```text
npx -y mcp-yandex-kit@latest
```

### Проектный runtime

В исходниках реализован явный режим `--project-config <absolute-binding-path>`.
Для установленного `@latest` он станет доступен только после согласованного
выпуска core, MCP и setup-навыка. Без аргумента сохраняется env-режим; неверный
аргумент или ошибка проектной привязки не переводит процесс в env-режим.

`packages/core/src/connections.mjs` задаёт единый формат хранения для runtime и
setup. Codegen поставляет навыку идентичную самодостаточную копию, не зависящую
от исходников монорепозитория. Binding версии 1 содержит только UUID
`connection_id`; приватная запись вне репозитория содержит токен, ожидаемый
`store_id` и необязательные `store_name`/`store_url`. Setup и runtime разрешают
один корень, включая `YANDEX_KIT_CONNECTIONS_DIR`; setup записывает его в
клиентскую MCP-конфигурацию. В проектном режиме унаследованные токен и base URL
игнорируются: секрет отправляется только на официальный API.

При запуске runtime сверяет `get_store` с сохранённым ID до создания транспорта
и регистрации инструментов. Проверка выполняется один раз на процесс; несовпадение,
недоступный токен или ошибка чтения не позволяют открыть рабочий MCP, включая
мета-инструменты.
После успешной проверки процесс использует один неизменяемый `KitClient` и
снимок подключения; обновление файлов требует нового MCP-процесса. Имя магазина
передаётся в локальном описании сервера, но не добавляется в схему инструментов
или телеметрию. GET-only повторы сохраняются.

Проектный setup использует CAS-ревизии, блокировки подключения/конфигов и приватный
журнал транзакции. Секрет публикуется раньше привязки и клиентских файлов; при
ошибке откатываются только принадлежащие транзакции ревизии. Конкурентная правка
остаётся нетронутой и возвращает конфликт. Старые секреты при смене магазина
сохраняются для других копий; автоматической очистки нет. На POSIX приватные
каталоги имеют `0700`, файлы `0600`; Windows DACL требует отдельной нативной приёмки.

Область client entry, миграция bundled/global серверов, команды проверки и правила
работы с токеном описаны в [INSTALLATION.md](INSTALLATION.md). Тесты с временными
проектами и recording fetch подтверждают четыре независимых подключения и общий
binding двух агентов; они не подтверждают реальную видимость plugin-инструментов
во всех версиях Codex/Claude Code. Нативная multi-project приёмка ещё не выполнена.

### Телеметрия использования

Сервер отправляет анонимные события на `usage.gistrec.cloud`, чтобы считать
активные установки и востребованность инструментов. В событии только
обезличенные технические поля: случайный идентификатор установки (UUID в
`~/.config/mcp-yandex-kit/instance-id`), тип события (`server_start` /
`tool_call`), **имя** вызванного инструмента, версия пакета, имя и версия
AI-приложения из MCP-handshake, версия Node.js и ОС.

Токен магазина, данные магазина, аргументы вызовов, тексты запросов и
IP-адреса не отправляются и не сохраняются (реализация — `packages/mcp/src/telemetry.ts`).
Отправка идёт в фоне с таймаутом 2 с и молча пропускается при любой ошибке —
на работу сервера не влияет. Исключение — событие `startup_failed`: оно ожидается
перед выходом процесса, с закрытым значением причины `missing_token` или
`invalid_config`. Имена/ID/URL магазинов, connection ID, пути привязки и секретов
не становятся полями телеметрии. Отключение — `YANDEX_KIT_TELEMETRY=0`.

## Ограничения внешнего API

- API ограничивает магазин тремя запросами в секунду.
- Песочницы нет: обычное подключение работает с боевым магазином.
- Публичный API находится в статусе беты, поэтому контракт может меняться. Снимок спецификации хранится в репозитории, а CI проверяет дрейф сгенерированных файлов.
- Секрет вебхука возвращается только при создании. Алгоритм проверки подписи входящих запросов Яндексом в используемой спецификации не документирован.
- API не предоставляет настройки оплаты и доставки и не позволяет launch-check самостоятельно создать и оплатить тестовый заказ.

## Генерация и проверки

Codegen создаёт реестр операций, TypeScript-типы, доменные навыки и [TOOLS.md](TOOLS.md) из сохранённой OpenAPI-спецификации. CI работает на Node.js 20, 22 и 24 и проверяет:

- типы и сборку;
- модульные и сценарные тесты;
- setup-сценарий;
- отсутствие дрейфа сгенерированных файлов.

Live E2E запускается отдельно только при наличии секретного токена тестового магазина.
