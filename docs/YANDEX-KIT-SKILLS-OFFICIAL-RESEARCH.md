Дата проверки: 2026-09-04.

Источники:

  внутреннего монорепозитория через синк (`.piglet-meta.json`, `.mapping.json`).

- `ztemerbekov/a1-yandex-kit-skills` — `main` @ `998afb6`, релиз 1.5.0.

## 0. Короткий вывод

Два набора решают пересекающиеся задачи принципиально разной архитектурой.

| | `yandex/kit-skills` | A1 |
| --- | --- | --- |
| Транспорт | нет MCP: скилл вызывает собственный CLI через Bash | MCP-сервер `mcp-yandex-kit` (84 инструмента) |
| Зависимости | Python 3, больше ничего | Node.js 20+, `npx`, сеть до npm-реестра |
| Где живёт токен | общий файл `~/.yandex-kit-skills/kit_api.token`, mode 600 | открытым текстом в пользовательском конфиге AI-клиента |
| Как токен вводится | одноразовая страница на `127.0.0.1` (десктоп) либо чат/ENV (hosted) | всегда в чат |
| Состав | 4 скилла, ~10 200 строк Python | 11 скиллов + MCP-сервер + генерация из спеки |
| Покрытие API | публичный API + экспериментальный контур витрины | 162 операции публичного API, витрины нет |
| Клиенты | Claude Code, Codex | 9 профилей, включая GUI без Bash |
| Тесты | в репозитории отсутствуют (внутренний пакет) | 422 юнит-теста в репозитории |

**Что стоит забрать (по убыванию ценности):** локальная страница ввода токена;
правило «маршрут выбирает окружение, а не пользователь»; правило о недоверенном
тексте из магазина; маскирование персональных данных в выводе; карта «чего в
публичном API нет» с маршрутом в кабинет; таблица перевода с языка API на язык
владельца магазина; онбординг «сначала что умею, потом токен»; per-skill
`AGENTS.md`; `user-invocable` / `allowed-tools` во фронтматтере.

**Что забирать не нужно:** телеметрию заголовками (у нас другой, более узкий
контракт), self-update с перезаписью установленных файлов, вендоренную копию
OpenAPI, отказ от MCP.

**Что у нас объективно сильнее и терять нельзя:** проверка токена реальным
вызовом до записи в конфиг, бэкап и откат конфига по хешам, девять клиентских
профилей, server wildcard, генерация скиллов и документации из спеки с проверкой
дрейфа в CI, сценарные скиллы (оператор, доктор каталога, промо-лаунчер,
launch-check).

## 1. Как устроен `yandex/kit-skills`

### 1.1 Состав

| Скилл | Назначение | Токен | Объём |
| --- | --- | --- | --- |
| `yandex-kit-cabinet` | точка входа: каталог, цены и остатки, заказы, промо, коллекции, вебхуки; плюс два агента кабинета — `ask analyst` (данные магазина) и `ask support` (документация кабинета) | нужен | SKILL.md 400 строк, 8 справочных страниц, `kit.py` 1721 строка |
| `kit-store-checkup` | еженедельная ревизия: 12 проверок, `finding_id` для сравнения прогонов | нужен | SKILL.md 191, `checkup.py` 1012 |
| `kit-storefront-constructor` | витрина: страницы, секции, версии, публикация полной заменой, загрузка медиа; здесь же живёт страница ввода токена | нужен | SKILL.md 213, `kit.py` 1952 + `kitlib/` ~3100 |
| `kit-custom-sections` | сборка кастомной секции (html + css + json_schema) из 14 верифицированных паттернов, полностью офлайн | не нужен | SKILL.md 156, `section.py` 579 + `seclib/` ~1850 |

Скиллы явно передают задачи друг другу: `checkup` не имеет ни одного пишущего
глагола и отдаёт каждое исправление в `cabinet`; `custom-sections` не делает ни
одного HTTP-запроса и печатает готовые команды `storefront-constructor`.

### 1.2 Структура одного скилла

```
skills/<name>/
├── SKILL.md            # фронтматтер + контракт работы (для агента-исполнителя)
├── AGENTS.md           # контракт правки скилла (для агента-разработчика)
├── agents/openai.yaml  # слой совместимости с Codex
├── references/         # доменные страницы, грузятся по требованию
└── scripts/*.py        # клиент, Python 3 stdlib only
```

Три решения здесь заметно отличаются от нашего:

1. **`SKILL.md` и `AGENTS.md` разведены по назначению.** `SKILL.md` — «как
   работать с магазином», `AGENTS.md` — «какие инварианты нельзя сломать, когда
   правишь этот скилл». Второй файл открывается фразой «First read parent
   `../../AGENTS.md`». У нас весь этот слой — один корневой `CLAUDE.md`.

2. **Фронтматтер несёт `user-invocable: true` и
   `allowed-tools: Bash(scripts/kit.py:*)`.** Второе — реальное ограничение
   поверхности: скилл не может дотянуться ни до чего, кроме своего клиента. У
   нас во фронтматтере только `name`, `description`, `compatibility`,
   `metadata`.

3. **Прогрессивное раскрытие.** `SKILL.md` держит правила и карту, детали лежат
   в `references/` и грузятся страницей под задачу («load only the page the task
   needs»). У нас пять сгенерированных доменных скиллов не имеют `references/`
   вообще — вся доменная плотность лежит в теле `SKILL.md` (например,
   `a1-yandex-kit-catalog/SKILL.md` — 248 строк сплошной прозы); из
   сгенерированных `references/` есть только у роутера `a1-yandex-kit` — один
   `merchant-communication.md`, который создаёт `gen-skills.ts`.

### 1.3 Контракт исполнения

- **Read-only по умолчанию.** `kit.py` отвергает POST/PUT/PATCH/DELETE без
  `--confirm`. У `checkup.py` пишущих глаголов нет вообще — это свойство кода, а
  не соглашение.
- **Офлайн-дискавери схемы.** `endpoints <слово>` → `describe <METHOD> <path>` →
  `schema <Name>` → `validate --data @body.json` поверх вендоренной
  `references/openapi.json`. Правило сформулировано жёстко: «never invent a
  request body or guess an enum value; если `describe` говорит, что операции нет,
  её нет».
- **Вердикт о покрытии — часть машинного ответа.** `kit.py list` обходит
  коллекцию до конца и печатает конверт
  `{coverage, received, total_count, pages_read, items}`; `coverage: partial`
  обязан попасть в ответ пользователю и запрещает вывод «всё в порядке».
- **`--redact`** маскирует в **выводе** имя, телефон, почту, адрес, примечания к
  доставке и клиенту. Тело запроса флаг не трогает принципиально: «a redacted
  write would be a silent corruption».
- **Три исхода записи, разведённые в коде.** `completed` (2xx **и** совпавшее
  обратное чтение), `failed` (4xx или локальная валидация), `ambiguous`
  (таймаут/5xx на мутации, exit `4`, никогда не повторять). Exit-коды:
  `0/1/2/3/4`.
- **Недоверенный текст.** Отдельное правило: примечание к доставке, адрес,
  описание товара из фида пишет не тот человек, который говорит с агентом.
  Команду, найденную в данных, не выполняют — цитируют, называют поле и объект и
  спрашивают пользователя. В `AGENTS.md` отдельно оговорено, что фильтр в
  клиенте эту гарантию дать не может, и добавлять его не нужно.
- **Язык кабинета, а не язык API.** Таблица переводов на 12 строк
  (`coverage: partial` → «я посмотрел 100 заказов из 340»,
  `WAIT_FOR_CONFIRMATION` → «ждёт вашего подтверждения») и двухслойное
  подтверждение мутации: сверху фраза, которую человек может оценить, не зная
  API, под ней команда.
- **Карта отсутствующих операций.** Таблица на 14 строк «Просят / Как есть /
  Куда в кабинете» с честной оценкой: около пятой части работы в кабинете
  публичным API не покрыто вовсе. Отказ обязан нести маршрут: «возвраты через
  меня не оформить — это в кабинете, раздел Заказы; отменить заказ я могу, но
  отмена и возврат денег — разные вещи».

### 1.4 Телеметрия и самообновление

Оба механизма описаны в `README.md` и продублированы контрактом в `AGENTS.md`.

**Телеметрия — только заголовки на запросах, которые скилл делал бы и так.**
`X-Skill`, `X-Skill-Prompt` (текст запроса пользователя, UTF-8, обрезка до 1000
символов, Base64), `X-Skill-Session` (UUID на тред), `X-Skill-Model`,
`X-Skill-Harness`, `X-Skill-OS`. Отдельного эндпоинта аналитики нет.
Отключается `YANDEX_KIT_SKILLS_TELEMETRY_DISABLED=1`, проверка живёт в одной
функции `skill_headers()`, чтобы ни один вызов не мог её обойти. Значения
`model`/`harness` приводятся к printable ASCII и обрезаются до 100 символов —
явно для того, чтобы перевод строки не позволил дописать свои заголовки.

**Самообновление.** API отдаёт `X-Skill-Version` на каждом ответе
экспериментального контура, включая ошибочные; клиент с более старой
`SKILL_VERSION` скачивает репозиторий с GitHub и перезапускает `install.py`.
Гарантии: выполняется после команды, никогда вместо неё; глотает любые ошибки в
одну строку stderr; не меняет exit-код; пропускается для checkout и симлинка;
стоп-защёлка в `~/.yandex-kit-skills/update-state.json` не даёт повторить одну и
ту же целевую версию. Отдельный выключатель
`YANDEX_KIT_SKILLS_AUTOUPDATE_DISABLED=1` — намеренно не тот же, что у
телеметрии: «one governs what leaves your machine, the other what arrives on it».

### 1.5 Установка

`install.py` — 208 строк stdlib: находит `skills/*/SKILL.md` и копирует каталог
в `~/.claude/skills/` и `~/.codex/skills/`. Агент считается установленным, если
существует его домашний каталог; если не найден ни один — ставит для обоих и
говорит об этом. Флаги `--dry-run`, `--agent`, `--skill`. Репозиторий
одновременно является Claude-плагином и маркетплейсом
(`/plugin marketplace add yandex/kit-skills`).

Отдельного внимания стоит финальный экран установщика: он написан для владельца
магазина, а не для того, кто запустил команду, — перечисляет по-русски, что
теперь можно поручить ассистенту, даёт ровно два следующих шага (перезапустить
ассистента, написать «подключи мой магазин Яндекс.Кит») и четыре примера фраз.

### 1.6 Витрина и кастомные секции

Это область, которой у A1 нет вообще.

- `kit-storefront-constructor` работает на **экспериментальном контуре**
  `/api/experimental/v1` плюс отдельный BFF витрины без авторизации. Единственный
  транспорт записи — полная замена `PUT /constructor/content` за
  `content push --confirm`, с CAS через `base_version_id`, одним перечитыванием
  на 409 и без автоматических повторов. Локальные гейты (страница не потеряна,
  alias не изменился, настройки валидны, копии композитных секций синхронны)
  срабатывают до подтверждения и полностью офлайн.
- `content push --no-publish` кладёт правку как proposal-версию, не показывая её
  витрине. Прописан отдельный «old-server guard»: сервер без этой раскатки молча
  игнорирует `activate` и **публикует** правку — клиент ловит это по отсутствию
  `active_version_id` в ответе и выходит с кодом `4`.
- `kit-custom-sections` — 14 паттернов, 94 разрешённых тега, биекция
  `{{settings.X}}` ↔ `properties` json_schema, запрет `:global(`, запрет
  хардкода цветов вместо `var(--ys-*)`. Пятиуровневая шкала проверки L0–L4 с
  явной фразой на каждый недоступный уровень.

Статья при этом сообщает продуктовую новость: кастомные секции стали доступны
всем пользователям Яндекс KITᵝ (раньше — только тестировщикам), HTML и CSS
поддерживаются, JavaScript и внешние скрипты — нет.

## 2. Сопоставление с A1

### 2.1 Где A1 сильнее

1. **MCP-сервер вместо Bash-клиента.** Скиллы Яндекса требуют возможности
   запускать процессы; в GUI-клиентах без Bash (Claude Desktop, Kimi Desktop,
   Hermes, embedded OpenClaw) они неприменимы. У нас девять клиентских профилей
   и документированная лестница совместимости для неизвестного клиента.
2. **Подключение проверяется до записи.** `smoke-token` поднимает
   `npx mcp-yandex-kit@latest`, выполняет реальный `get_store` и только после
   успеха пишет токен. Неверный токен в конфиг не попадает. У Яндекса страница
   принимает токен после локальной проверки формата, а доступ проверяется уже
   потом, командами `whoami` / `store`.
3. **Конфиг клиента трогается аккуратно.** Бэкап, режим `0600`, откат по
   совпадению контрольных хешей, сохранение чужих MCP-серверов, обход коллизии
   имени через `a1-yandex-kit-global`.
4. **Генерация из спеки.** Шесть доменных скиллов, `docs/TOOLS.md` и
   `packages/core/src/generated/**` производятся `npm run gen`, CI падает на
   дрейфе. У Яндекса справочные страницы поддерживаются вручную (в `AGENTS.md`
   прямо запрещено копировать таблицы полей в страницы — именно потому, что они
   протухают).
5. **Тесты в репозитории.** 422 юнит-теста. Оценочные наборы Яндекса живут во
   внутреннем пакете и опубликованы не были — проверить их поведение снаружи
   нельзя.
6. **Сценарные скиллы.** Оператор, доктор каталога, промо-лаунчер, проверка
   запуска. У Яндекса из этого класса есть только `kit-store-checkup`, и он
   уже read-only.
7. **Клиентский слой API.** Токен-бакет, ретраи на сети/5xx/429/`LIMIT_EXCEEDED`
   только для GET, автопагинация `listAll`, merge-patch и multipart по спеке,
   bulk-операции до 5000 позиций.

### 2.2 Пробелы A1, которые видно на фоне официального набора

| № | Пробел | Что есть у Яндекса | Риск для нас |
| --- | --- | --- | --- |
| 1 | Нет правила о недоверенном тексте из магазина | `SKILL.md` rule 8 + `workflow.md` | Оператор читает `delivery_notes`, примечания и описания из фида и не имеет ни одной инструкции о том, что там может быть команда. Усугубляется тем, что мы штатно предлагаем server wildcard — host-подтверждений, которые могли бы поймать неожиданный вызов, после этого нет |
| 2 | Нет маскирования персональных данных | `--redact` | «Выгрузи заказы за неделю» тянет в переписку ФИО, телефоны и адреса, которые задаче не нужны |
| 3 | Нет карты «чего в публичном API нет» | таблица на 14 строк с маршрутом в кабинет | Отказы формулируются на ходу; риск изобрести похожую операцию (отмена вместо возврата) или уйти в угадывание пути |
| 4 | Токен всегда идёт через чат | локальная страница для десктопа | `docs/INSTALLATION.md` вынужден честно писать: «после отправки setup-сценарию остаётся в истории чата» |
| 5 | Нет `user-invocable` / `allowed-tools` | есть в каждом скилле | Поверхность скилла ничем не ограничена |
| 6 | Нет per-skill `AGENTS.md` | есть в каждом скилле | Инварианты сценарных скиллов не записаны там, где их правят |
| 7 | Вердикт о покрытии — только инструкция | машинный конверт `list` | Оператору предписано считать `total_count` вручную; ошибка тихая |
| 8 | Онбординг начинается с токена | шаг 0 «сначала скажи, что умеешь» | Первое сообщение продукта — запрос учётных данных |
| 9 | `merchant-communication.md` — 37 строк без примеров | таблица переводов + шаблон двухслойного подтверждения | Правило есть, следовать ему не по чему |
| 10 | Витрина и кастомные секции не покрыты | два скилла | Продуктовый разрыв, не дефект |

### 2.3 Расхождение, которое нужно проверить отдельно

**Лимит запросов.** A1 держит токен-бакет на **3 rps** (`packages/core/src/client.ts:174`)
и заявляет 3 rps в `a1-yandex-kit/SKILL.md` и во всех доменных скиллах.
Официальный `references/api.md` Яндекса говорит: «Rate limit: **10 requests/second
per store**. The tool retries `429` responses automatically». Публичная
документация (`yandex.ru/dev/kit/ru/`) ссылается на раздел «Ограничения
запросов», но его страница по угаданным адресам не открылась — цифру я не
подтвердил ни одним первоисточником.

Если 10 rps верны, мы втрое замедляем каждый массовый импорт и каждый обход
каталога без причины. Это дешёвая проверка (замер на тестовом магазине) с
заметным выигрышем — вынес отдельным пунктом в рекомендации.

Второе расхождение помельче: A1 описывает `LIMIT_EXCEEDED` как HTTP 400,
официальный клиент ретраит `429`. Похоже, контур отдаёт оба; наш клиент это уже
учитывает (`RETRYABLE_400_CODE`), но формулировка в скиллах говорит «HTTP 400
(not 429)» категорично и может ввести модель в заблуждение.

## 3. Что заимствовать

Оценка объёма — в человеко-днях, для одного разработчика, включая тесты и
правку документации.

| № | Что | Источник | Польза для A1 | Объём | Приоритет |
| --- | --- | --- | --- | --- | --- |

### 3.1 Что сознательно не берём

- **Телеметрия заголовками.** Контракт Яндекса требует отправлять текст запроса
  пользователя (до 1000 символов) в их API. Наш канал (`usage.gistrec.cloud`)
  шлёт только идентификаторы, имена и версии и никогда — данные или аргументы.
  Переход на их модель был бы регрессом по приватности, а не улучшением.
- **Self-update с перезаписью установленных файлов.** Скачивание и запуск кода с
  GitHub без явной команды пользователя не ложится в наш контракт. У нас
  `npx mcp-yandex-kit@latest` и `npx skills update` решают ту же задачу без
  записи в чужие каталоги.
- **Вендоренная `openapi.json`.** У нас своя спека (`specs/kit-swagger.openapi.json`,
  162 операции) и генерация от неё.
- **Отказ от MCP в пользу Bash-клиента.** Их путь дешевле по зависимостям, но
  закрывает GUI-клиентов, которых мы поддерживаем.

### 4.1 Что показано в статье

2. Написать: «Установи skill из этого GitHub-репозитория:

> страницу в браузере для установки API-ключа. Чтобы получить токен, перейдите в

Три содержательных изображения (плюс обложка). **Клиент на скриншотах — не

с подсказкой «Попробуйте режим аннотирования». Текст статьи при этом называет

рассчитывают на более широкий круг клиентов, чем декларируют.

### 4.3 Сверка с исходниками

Всё показанное подтверждается кодом `kitlib/tokenweb.py`.

| Что видно | Чем подтверждается |
| --- | --- |
| «Ссылка действует 5 минут» | `DEFAULT_TIMEOUT_SECONDS = 300.0` (максимум — `MAX_TIMEOUT_SECONDS = 3600.0`) |
| «и только один раз» | `secrets.token_urlsafe(32)` в URL, сравнение через `compare_digest`; после успешного сохранения сервер отдаёт терминальную страницу и выходит |
| Плейсхолдер `yakit_…` | `TOKEN_PREFIX = "yakit_"`; тот же префикс используется в `TOKEN_PATTERN` для вычищения токена из любого печатаемого текста |
| «Токен остаётся на этом компьютере» | сокет биндится только на `127.0.0.1`; адрес пира обязан быть в `{127.0.0.1, ::1, ::ffff:127.0.0.1}`, а заголовок `Host` — в `{127.0.0.1, localhost, [::1]}`. Вторая проверка — защита от DNS-rebinding |
| Токен не попадает в лог | `log_message()` переопределён пустым телом; токен приходит в теле POST, не в URL |
| Страница ничего не грузит извне | `Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'; form-action 'self'; base-uri 'none'; frame-ancestors 'none'`, плюс `Referrer-Policy: no-referrer`, `Cache-Control: no-store`, `X-Content-Type-Options`, `X-Frame-Options: DENY` |
| Ограничение перебора | `MAX_WRONG_SECRETS = 20`, после чего сервер останавливается сам; тело запроса ограничено `MAX_BODY_BYTES = 8192` |
| Куда ложится токен | `~/.yandex-kit-skills/kit_api.token`, mode 600 — общий файл для всех скиллов Кита |

Отдельно проверен отказ в hosted-сессии. `unreachable_reason()` возвращает
причину и `token web` **выходит до открытия сокета**, если: заданы `SSH_CONNECTION`
/ `SSH_CLIENT` / `SSH_TTY`; существует `/.dockerenv` или `/run/.containerenv`; в
`/proc/1/cgroup` есть маркер `docker`/`containerd`/`kubepods`/`lxc`/`libpod`; это
Linux без `DISPLAY` и `WAYLAND_DISPLAY`; либо `webbrowser.get()` бросает ошибку.
Текст отказа — не «ошибка», а пронумерованный маршрут: сначала `KIT_TOKEN` в
настройках окружения сессии, потом токен в переписке через `token save` из
stdin, и только третьим — `--force`, «only when the user already forwards this
host's port to their browser».

### 4.4 Что есть в репозитории, но не показано в статье

- **Ручной маршрут без агента.** `kit.py token save` со скрытым вводом
  (`getpass`), и порядок разрешения токена `KIT_TOKEN` → `KIT_TOKEN_FILE` →
  файл по умолчанию.
- **Приоритет внутри hosted-маршрута.** Статья говорит просто «можно передать
  текстом или файлом в чат». `SKILL.md` требует сначала предложить
  `KIT_TOKEN` в настройках окружения или секретов сессии, потому что тогда
  значение не попадает в переписку, и только если пользователь до них не
  дотягивается — брать токен в диалоге.
- **Проверка доступа.** `kit.py whoami` (учётка и роль) и `kit.py store` (какой
  магазин) как обязательный шаг после сохранения.
- **Свойства самого токена.** Один токен = один магазин; показывается ровно один
  раз, в списке остаётся маска вида `**************Buf3`; несколько токенов на
  магазин допустимы; скомпрометированный удаляется в кабинете.
- **Запрет на командную строку.** «Never put the token on a command line, in any
  route» — правило без исключений на всех поверхностях.

**Одна неточность статьи.** «Если помощник работает локально на десктопе, **после
установки** он откроет страницу в браузере» — на самом деле страница открывается
не после установки, а когда пользователь просит подключить магазин и
`token status` вернул exit 2. Скриншот 2 это и показывает: между установкой и
страницей есть отдельный запрос пользователя. Мелочь, но она задаёт неверное
ожидание («сейчас само откроется»).

### 4.5 Сценарий A1 сегодня

`skills/a1-yandex-kit-setup/SKILL.md`, семь шагов:

1. Определить клиента (9 профилей) или спросить одним вопросом;
   `status --client <client>` проверяет Node.js 20+ и исполняемый `npx` **до**
   запроса токена и до любой правки конфига.
2. Сверить профиль совместимости; на несовпадении — лестница из
   `references/compatibility.md`.
3. **Запросить токен в чате.** Дословно: «Вставьте его сюда — я привяжу его к
   приложению и не буду повторять в ответе. Токен останется в истории этого чата
   и будет сохранён в пользовательском конфиге приложения». Затем `smoke-token`
   — реальный `get_store` через поднятый `npx mcp-yandex-kit@latest`. Неверный
   токен в конфиг не пишется, цикл повторных попыток не ограничен.
4. `configure` — токен идёт через stdin, не через аргументы; бэкап
   существующего конфига, режим `0600`, чужие серверы не трогаются, при
   коллизии имени используется `a1-yandex-kit-global`.
5. `client-check` + `smoke`; при провале — `rollback` по совпадению хешей.
6. Один раз предложить «Работу без остановок» (server wildcard) с явным
   предупреждением про удаления, заказы, промо и настройки.
7. Одна инструкция по перезапуску, один короткий результат.

Сильные стороны, которых нет у Яндекса: проверка токена боевым вызовом до
записи; бэкап и откат конфига по хешам; явно прописанный сценарий повторного
подключения и замены токена; работа с GUI-клиентами.

Слабые стороны на фоне Яндекса:

- **Токен всегда проходит через чат** — и на десктопе тоже, где этого можно не
  делать.
- **Хранится открытым текстом** в пользовательском конфиге клиента, а не в
  отдельном файле с правами 600. Мы это честно пишем в `INSTALLATION.md`, но
  честность здесь не заменяет решение.
- **Конфигурация привязана к клиенту**: при переходе на другое приложение
  подключение нужно повторять целиком. У Яндекса общий токен-файл виден всем
  скиллам и всем агентам сразу.
- **Требуется сеть до npm-реестра** уже на этапе проверки токена, и в
  песочнице (Codex) нужен режим с сетью с первой попытки.
- **Установщик запускается только явным вызовом** `$a1-yandex-kit-setup`; фраза
  «Подключи Яндекс KIT» его не запускает (`INSTALLATION.md`, шаг 3). У Яндекса
  вход в подключение — обычная фраза, что и показано на скриншоте 2.

### 4.6 Что взять в подключение A1

По убыванию отдачи:

1. **Локальная одноразовая страница ввода токена (P0).** Node-аналог `token web`
   внутри `setup.mjs`: `http.createServer` на `127.0.0.1:0`, одноразовый secret
   в URL, проверка адреса пира и заголовка `Host`, CSP `default-src 'none'`,
   отключённое логирование, лимит тела, дедлайн 300 с, лимит неверных попыток,
   выход после первой успешной записи. Токен из формы идёт сразу в `configure`,
   минуя чат. Ветка нужна только там, где мы и так пишем в конфиг на этой же
   машине, — то есть в подавляющем большинстве наших сценариев.
2. **Явный детект hosted-сессии (P0).** Порт `unreachable_reason()`: `SSH_*`,
   `/.dockerenv`, `/run/.containerenv`, cgroup PID 1, Linux без дисплея,
   отсутствие браузера. Если страница неприменима — не предлагать её и не
   печатать мёртвую ссылку, а сразу давать маршрут: переменные окружения или
   секреты сессии → токен в чате. Формулировка Яндекса здесь образцовая: «Это
   нормальный, предусмотренный маршрут», а не извинение.
3. **Порядок маршрутов в hosted-сессии (P0, дёшево).** Сейчас мы сразу просим
   токен в чате. Правильнее: сначала предложить задать токен в настройках
   окружения/секретов сессии, и только если пользователь до них не дотягивается
   — принять в диалоге, сказав, что значение останется в истории, и напомнив про
   отзыв в **Настройки → API**.
4. **Отдельный файл токена как второй источник (P1).** Даже сохраняя запись в
   конфиге клиента, поддержать `YANDEX_KIT_TOKEN_FILE` и общий файл
   `~/.a1-yandex-kit/token` (mode 600) — тогда переход на другой клиент не
   требует повторного ввода, а токен перестаёт лежать открытым текстом там, где
   его читают все инструменты приложения.
5. **Раскрытие того, что уходит наружу, в момент настройки (P1).** Яндекс
   говорит про телеметрию одной фразой при подключении, а не прячет её в README.
   У нас есть `YANDEX_KIT_TELEMETRY=0`, и он нигде не звучит в разговоре.
6. **Онбординг перед запросом токена (P1).** Первое сообщение — три-четыре вещи,
   которые теперь можно поручить, своими словами; токен — как один оставшийся
   шаг. У нас первое сообщение установщика это запрос токена.
7. **Запуск подключения обычной фразой (P2).** Требование явного
   `$a1-yandex-kit-setup` — наша сознательная защита от ложных срабатываний, но
   она стоит нам самого частого сценария первого дня. Стоит хотя бы обрабатывать
   «подключи мой магазин Яндекс KIT» как приглашение предложить запуск скилла.

## 5. Открытые вопросы

1. **Лимит 3 vs 10 rps** — нужен замер на тестовом магазине или ответ поддержки
   Кита. Дешевле всего проверить, отдаёт ли контур `LIMIT_EXCEEDED` при 4–9 rps.
2. **`allowed-tools` для MCP-инструментов** — нужно проверить на живых клиентах,
   как `allowed-tools: mcp__yandex-kit__*` во фронтматтере скилла сочетается с
   уже выданным server wildcard и не создаёт ли двойной слой ограничений.
3. **Экспериментальный контур витрины.** `kit-storefront-constructor` и
   `ask analyst`/`ask support` работают на `/api/experimental/v1`, который сам
   Яндекс называет находящимся вне опубликованного справочника и способным
   измениться без предупреждения. Прежде чем планировать конструктор витрины у
   нас, стоит решить, готовы ли мы зависеть от непубличного контура.
4. **Ассистенты кабинета (`ask analyst` / `ask support`).** У нас аналога нет, а
   это два эндпоинта под тем же токеном, закрывающие целый класс запросов
   («почему упали заказы», «как настроить самовывоз»). Проверить, доступны ли
   они на публичном контуре — если да, это самое дешёвое расширение
   функциональности из всего списка.
